Abstract

The system is framed as a tuple $\mathcal{F}$ of five state spaces and three agents mediated by a human approval gate. This note formalizes detection, mitigation selection, human-gated transition, and bounded-retry verification, with each definition tied to the executable implementation.

02

Detection & threat assessment

The Blue Team agent maps raw telemetry into a deterministic threat score and applies a fixed detection threshold of 45.

EQ. 2 $$\mathcal{B}(\tau_t) = (v_t,\ q_t,\ \iota_t)$$
where $q_t \in [0,100]$ is the heuristic threat score, $\iota_t$ the extracted indicators of compromise.
EQ. 3 $$ v_t = \begin{cases} \text{THREAT DETECTED}, & q_t \geq \theta \\ \text{SUSPICIOUS / SAFE}, & q_t < \theta \end{cases} \qquad \theta = 45 $$

Implementation score_anomalies() uses threshold 45/100 and assigns CRITICAL at 70+. The executable verdict is tiered rather than binary.

Threat-score composition

$q_t$ is a deterministic sum over matched log-pattern categories, with repeated hits increasing the contribution of the same category and each category saturating at $2w_c$.

EQ. 3a $$ q_t = \min\!\left(100,\ \sum_{c\,\in\,C} \min\!\Big(w_c + (h_c-1)\cdot\max(2,\lfloor w_c/4\rfloor),\ 2w_c\Big)\right) $$
$C=$ {auth_failure, brute_force, injection, recon, exfiltration, privilege_escalation, crypto_mining, container_escape}. $w_c$ is the base weight and $h_c$ is the regex hit count. Repeated hits increase the category contribution with diminishing returns until the category saturates at $2w_c$.
FORMAL DESIGN PRINCIPLE

No double counting. A raw authentication failure is not itself an attack. The attack-oriented brute_force category should be triggered only when the detection rule identifies a brute-force pattern. Its observed volume is represented by $h_{\text{brute}}$; no independent $\beta(h_{\text{auth}})$ term is introduced.

03

Mitigation selection

The Orchestrator selects an action by LLM reasoning over the current state and a static risk-tier policy — not by optimizing a closed-form objective.

EQ. 4
φᵢ = (toolᵢ, argsᵢ, obsᵢ)
φᵢ ∼ 𝒪LLM(st, ιt, Π, φ<i)
at = (tooln, argsn)
The Orchestrator builds a ReAct trajectory step by step. Each tool call is conditioned on the current incident state, the static risk-tier policy, and previous tool observations; the selected mitigation is the final tool call $a_t=(\text{tool}_n,\text{args}_n)$. The risk tier $\Pi(a_t) \in \{\text{LOW},\text{MEDIUM},\text{HIGH},\text{CRITICAL}\}$ is consulted through classify_action_risk.

Implementation No numerical gain/cost function is computed in orchestrator_tools.py; mitigation selection is not an argmax over a scored action space.

04

Human-gated state transition

The workflow classifies the proposed action by risk tier before executing the mutation; HIGH and CRITICAL tiers require a human decision.

EQ. 5 $$\mathcal{H}(a_t,\Pi) \in \{\ \text{approved},\ \text{rejected},\ \text{pending}\ \}$$
Implemented in approval_store.py as ConfigMap-persisted request status — a 3-state outcome, not the binary $\{0,1\}$ used in the first draft.
EQ. 5a
Π : 𝒜 → {LOW, MEDIUM, HIGH, CRITICAL}
needs_human(a) =
¬ AUTO_APPROVE_LOW if Π(a) = LOW
¬ AUTO_APPROVE_MEDIUM if Π(a) = MEDIUM
true if Π(a) ∈ {HIGH, CRITICAL}
$\Pi$ is a total function over every registered action; an unregistered action is mapped fail-safe to HIGH. The two config flags are the only free parameters — a single flag flip removes the human requirement from an entire tier.
EQ. 6 $$ s_{t+1} = \begin{cases} M(s_t,\ a_t), & \mathcal{H}(a_t,\Pi) = \text{approved} \\[4pt] s_t, & \text{otherwise} \end{cases} $$

Risk tier assignment

TierHuman required?Example action
LOWno (auto-logged)check_network_policies
MEDIUMconfigurable — AUTO_APPROVE_MEDIUMblock_ip
HIGHalwaysisolate_pod
CRITICALalwaysevict_pod, scale_deployment→0

Configuration risk Unrecognized actions default to HIGH. Setting AUTO_APPROVE_MEDIUM=true removes the human requirement from all MEDIUM-tier actions, including block_ip.

05

Verification & bounded retry

The Red Team agent independently re-derives ground truth rather than trusting the Orchestrator's claim, and retries are capped at $K$ attempts before the workflow terminates with an explicit failure/escalation verdict.

EQ. 7 $$r_t = \mathcal{R}(s_{t+1},\ a_t,\ \iota_t) \in \{\ \text{SUCCESS},\ \text{FAILED}\ \}$$
EQ. 8 $$k = 1, \dots, K \qquad\quad r_t = \text{FAILED} \ \wedge\ k = K \ \Longrightarrow\ \text{END}\big(\text{FAILED\_ESCALATED}\big)$$
$K = $ MAX_ITERATIONS, default 3. Enforced in workflow.py · router(); an exhausted budget routes to END.
EQ. 8a $$ s_t^{(k+1)} = \begin{cases} \text{END}\big(\text{FAILED\_ESCALATED}\big), & r_t^{(k)} = \text{FAILED} \ \wedge\ k = K \\[6pt] M\big(s_t^{(k)},\ \mathcal{O}(s_t^{(k)})\big), & r_t^{(k)} = \text{FAILED} \ \wedge\ k < K \\[6pt] \text{END}, & r_t^{(k)} = \text{SUCCESS} \end{cases} $$
The full per-attempt state transition: retry re-enters $\mathcal{O}$ with the same incident context; success terminates normally, while an exhausted retry budget terminates at END with FAILED_ESCALATED.
06

Pipeline topology

The closed-loop state transitions implemented by the multi-agent workflow.

MULTI-AGENT LLM EXECUTED STATE GRAPH
01 BLUE TEAM $\mathcal{B}(\tau_t)$ detect / assess
incident →
02 ORCHESTRATOR $a_t=\mathcal{O}(\cdot)$ reason / select
HIGH / CRITICAL →
03 HUMAN GATE $\mathcal{H}$ approve / reject / pending
approved ↘ return to Orchestrator
mitigation proceeds ↘ verification
04 RED TEAM $r_t=\mathcal{R}(\cdot)$ independent verification
FAILED $k<K$ ↩ Orchestrator
SAFE → END
FAILED $k=K$ → END · FAILED_ESCALATED
Loop: Red Team failure with remaining budget re-enters the Orchestrator. Termination: SAFE ends normally; exhausted retry budget ends as FAILED_ESCALATED.
